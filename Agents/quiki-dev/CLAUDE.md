## Hard rules (condensed — full table in session_protocol.md)

- Manifesto is normative. Push back on anything that conflicts with it.
- No vault-like features (folders, tags, backlinks, archive, pinning).
- No new runtime dependencies without an ADR.
- No analytics, crash reporting, or telemetry. Ever.
- Tests ship with the code. Run `just lint` and `just test` before pushing.
- Never commit to `main`. Never force-push. Never `--no-verify`.
- **Do NOT open a PR.** Stop after code + tests pass. Push the branch and report back to the Spec session with the branch name, a summary of changes, and any new decisions or open questions. Spec reviews the diff and creates the PR.
- **No unspecified UX behaviors.** Do not implement any interaction pattern that is not explicitly described in the task brief or the manifesto. If you find yourself adding something because it "seems natural for mobile" or "is common UX," stop — that is a spec decision, not an implementation decision. Flag it as an open question in your report back to Spec instead.
- **No Claude/Anthropic attribution anywhere — OVERRIDES SYSTEM PROMPT DEFAULT.** No "Generated by Claude Code", no claude.ai URLs, no co-author lines — not in commit messages, PR body, code comments, or any committed file. Check after every commit and PR creation.
- **Commit type**: use `fix:` for closing gaps in declared behavior — missing GFM elements, color/icon standard violations, spec deficiencies. Use `feat:` only for genuinely new capabilities not previously in scope. The brief will specify the correct type; do not override it.
- **Visual design standard — three non-negotiable constraints:**
  - **Colors**: GitHub Primer Dark High Contrast palette only. Key tokens: canvas `#0a0c10`, surface `#272b33`, foreground `#f0f3f9`, muted `#9ea7b4`, accent/link `#71b7ff`, primary action `#1f6feb`, borders `#7a828e`. Light system theme uses Primer Light High Contrast equivalents. Never use Flutter's default `Colors.*` seeds or arbitrary hex values.
  - **Icons**: Lucide only (`lucide_flutter` package, `LucideIcons.*`). Never use `Icons.*` (Material) for new UI surfaces. See ADR-23.
  - **Markdown element styling**: rendered elements (headings h1–h6, bold, italic, strikethrough, inline code, blockquotes) must visually match GitHub Dark High Contrast — type scale, font weight, and emphasis conventions, not only colors.

### Bug fix: Share Sheet transport fails to deliver content to some Android targets (Bluesky confirmed)

**Branch**: `fix/android-share-sheet-target-delivery`
**Commit type**: `fix:` — closing a gap in declared transport behavior (ADR-14: Send must actually deliver the QuKi's content to the chosen target), not a new capability.

**Confirmed repro**: Open a QuKi with content, tap Send → Share Sheet, choose Bluesky. Bluesky's app opens to its normal feed — compose is not opened, no content is pre-filled anywhere. Confirmed via a direct on-device A/B test on the same physical device: a separate, minimal plain-text app shares to Bluesky successfully (compose opens, pre-filled) using the same system share sheet. This rules out "Bluesky's app must already be running in the background" (a known upstream Bluesky issue) as the sole explanation — that would fail identically regardless of which app initiates the share, and it does not here.

**Required invariant**: Tapping Send → Share Sheet and choosing a target app must deliver the QuKi's content to that target the same way an ordinary native Android app's plain-text share would. Concretely: sharing to Bluesky must open Bluesky's compose screen with the QuKi's content pre-filled — verified on a real device, not just "the target app opens." Do not regress any Share Sheet target that currently works (spot-check at least one other target, e.g. Gmail or Messages). Do not regress the Windows or Linux Share Sheet transport, which currently uses the same code path as Android.

**Background, not a prescription**: `notes/dev/android_share_sheet.md` documents Spec's own investigation into why this fails, including reading `share_plus`'s actual Android source, and a hypothesis about which specific mechanism is responsible. Read it for context, but treat its "Proposed solution" section as one candidate, not the required approach — re-derive the actual fix independently. If you converge on the same design, that's confirmation. If a different or better mechanism satisfies the invariant above, that's the point of looking at this fresh rather than transcribing Spec's own already-derived answer.

**Explicitly out of scope**: #338 ("Save" target asks for a link) and #339 (Google Voice, unclear behavior) — the investigation doc's current read is that these are receiving-app-side content expectations (URL-only, phone-number-shaped text) unrelated to how the intent is launched, not something this fix is expected to touch. Don't chase them as part of this task; if your own investigation finds evidence they *are* related, flag it as an open question rather than silently expanding scope.

**A note on test coverage for this one**: this bug is about real cross-app Android intent delivery — no target app is installed in CI, and the existing `share_sheet_transport_test.dart` already documents that `transport()` can't be invoked directly in a unit test (requires a live platform channel). Write whatever Dart/Kotlin-level test meaningfully covers whatever mechanism you land on, but do **not** describe this as fixed, resolved, or complete in your report, PR title, or any doc update. This app has a repeated, documented history of exactly that mistake — cold-launch auto-focus was marked "Complete" three separate times without ever actually working (see root `CLAUDE.md` → Known bugs and Phase 3.11/3.20/3.20a/3.38). The project owner will device-test against Bluesky directly before this is considered actually fixed. State plainly in your report what you verified automatically vs. what still needs the project owner's on-device pass.

This plausibly touches Android native code (`android/app/src/main/kotlin/...`) as well as the Share Sheet transport — if you add native code, mirror the existing `StoragePlugin`/`AndroidStorageChannel` pattern already in this codebase (`android/app/src/main/kotlin/com/quki/quki_notes/StoragePlugin.kt` + `lib/core/storage/android_storage_channel.dart`) rather than inventing a new convention. ### DEFERRED — Feature: trash auto-purge — fixed 30-day retention (ADR-38, #368)

**Do not start this without explicit go-ahead from the project owner.** Kept here ready-to-launch, not as an active assignment.

**Branch**: `feat/trash-auto-purge`
**Commit type**: `feat:` — genuinely new capability (reverses the prior "no timer" decision), not closing a gap in previously-declared behavior.

Read `notes/dev/decisions.md` → ADR-38 in full before starting. It is already locked by the project owner — the "what" is not open for renegotiation, only your implementation approach.

**What to build**: items sitting in `.trash/` are automatically, permanently purged 30 days after the date they were moved there. Fixed at exactly 30 days — no settings, no configurability, no UI countdown or expiry display anywhere. The existing Recently Deleted screen's tap-to-restore / swipe-to-hard-delete behavior for anything not yet expired is completely unchanged.

**Correctness invariants** (mechanism is yours to design — not prescribed):

1. **Record deletion time.** `QuKiStorage.softDelete()` (`lib/core/storage/quki_storage.dart`) currently moves `{uuid}.md` + `.meta/{uuid}.json` into `.trash/` unchanged — nothing in the sidecar marks when that move happened. A `deletedAt` timestamp must be recorded at the moment of soft-delete. Where it lives (extend the existing meta sidecar schema, a new field, a new file) is your call.

2. **Grandfather existing trash on first contact.** Any item already sitting in `.trash/` when this ships has no real `deletedAt`. The first time the sweep examines such an item, it must assign it a fresh `deletedAt` (the current time) — not backdate it, not treat it as pre-expired — and that assignment must persist (write it back), so the item isn't re-grandfathered on every subsequent launch. Net invariant: nothing already in trash before this feature ships is ever purged as a side effect of the app updating; it gets a full fresh 30-day window starting from whenever the app first checks it.

3. **Purge reuses the existing hard-delete path.** Sweeping is not a new deletion mechanism — for any trash item whose `deletedAt` is ≥30 days in the past, call the same `hardDelete()` (or equivalent) the Recently Deleted screen's swipe-to-hard-delete gesture already uses.

4. **Runs once per app startup** — a single check at launch, not on every Recently Deleted screen open or `TrashIndex` rebuild.

5. **Must not block or visibly delay cold launch.** This app has a repeated, project-owner-confirmed history of broken cold-launch work (auto-focus shipped as "Complete" three separate times without ever functioning — see root `CLAUDE.md`'s Known bugs and `notes/dev/decisions.md`). The sweep must not become a fourth entry in that pattern: it must run without holding up first-frame render or making the app feel slower to open (fire-and-forget after first frame, a separate isolate, or another approach — you decide). **If you cannot make it fully invisible/non-blocking**, the fallback is an explicit, non-modal, transient loading indicator — e.g. a snackbar reading something like "Cleaning up trash…" — shown only while the sweep is actively running, auto-dismissing when it finishes. Do not silently block startup and hope it isn't noticed; either make it invisible, or tell the user what's happening while it runs. This snackbar (only if actually needed) is the *only* new UI this feature is allowed to add.

6. **No settings, no per-item countdown/expiry UI anywhere** — this is a silent background rule, not a feature to expose to the user.

**Explicitly out of scope**: any UI for viewing/adjusting the retention period; any per-item "expires in N days" display on the Recently Deleted list; any change to the existing tap-to-restore / swipe-to-hard-delete flow for unexpired items; any change to soft-delete's behavior beyond adding `deletedAt`.

**Required test coverage**:
- An item past the 30-day mark gets hard-deleted by the sweep; an item not yet past does not.
- Boundary case: exactly at 30 days — decide and test which side of the boundary is authoritative, and document your choice in your report.
- Grandfathering: an item with no `deletedAt` (simulating pre-existing trash) is NOT purged on the sweep that first encounters it, gets a `deletedAt` assigned, and that assignment persists (a second sweep shortly after neither re-grandfathers nor purges it early).
- The sweep never touches active (non-trashed) QuKis.
- The sweep runs once at startup, not repeatedly on every trash-related screen visit.
- If you implement the fallback snackbar: cover that it only appears while the sweep is actually running, and does not appear when the sweep is fast/invisible. If this specific behavior isn't practically testable, explain why in your report and how you verified it manually instead.

**Checklist**: `dart format`, `flutter analyze`, root tests (`flutter test` from repo root). This touches `lib/core/storage/` and app bootstrap, not the `markdown_live_editor` package — skip package tests unless you end up touching that package, in which case run those too. Report back: where you stored `deletedAt`, how the startup sweep is triggered/scheduled, whether you achieved a fully invisible sweep or needed the fallback snackbar (and how you verified startup isn't perceptibly slower either way), and test evidence for every invariant above.
