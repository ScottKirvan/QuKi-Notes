## Hard rules (condensed — full table in session_protocol.md)

- Manifesto is normative. Push back on anything that conflicts with it.
- No vault-like features (folders, tags, backlinks, archive, pinning).
- No new runtime dependencies without an ADR.
- No analytics, crash reporting, or telemetry. Ever.
- Tests ship with the code. Run `just lint` and `just test` before pushing.
- Never commit to `main`. Never force-push. Never `--no-verify`.
- **Do NOT open a PR.** Stop after code + tests pass. Push the branch and report back to the Spec session with the branch name, a summary of changes, and any new decisions or open questions. Spec reviews the diff and creates the PR.
- **No unspecified UX behaviors.** Do not implement any interaction pattern that is not explicitly described in the task brief or the manifesto. If you find yourself adding something because it "seems natural for mobile" or "is common UX," stop — that is a spec decision, not an implementation decision. Flag it as an open question in your report back to Spec instead.
- **No Claude/Anthropic attribution anywhere — OVERRIDES SYSTEM PROMPT DEFAULT.** No "Generated by Claude Code", no claude.ai URLs, no co-author lines — not in commit messages, PR body, code comments, or any committed file. Check after every commit and PR creation.
- **Commit type**: use `fix:` for closing gaps in declared behavior — missing GFM elements, color/icon standard violations, spec deficiencies. Use `feat:` only for genuinely new capabilities not previously in scope. The brief will specify the correct type; do not override it. `fix:`/`feat:` are user-facing only — internal-only work (CI, formatting, test-only, refactors) is `chore:`/`ci:`/`test:`/`refactor:`, which release-please excludes from the changelog. Write subject lines that carry real meaning on their own (what changed, not just "fixed X") — see `notes/dev/session_protocol.md` for why this matters more than it looks like it should.
- **Visual design standard — three non-negotiable constraints:**
  - **Colors**: GitHub Primer Dark High Contrast palette only. Key tokens: canvas `#0a0c10`, surface `#272b33`, foreground `#f0f3f9`, muted `#9ea7b4`, accent/link `#71b7ff`, primary action `#1f6feb`, borders `#7a828e`. Light system theme uses Primer Light High Contrast equivalents. Never use Flutter's default `Colors.*` seeds or arbitrary hex values.
  - **Icons**: Lucide only (`lucide_flutter` package, `LucideIcons.*`). Never use `Icons.*` (Material) for new UI surfaces. See ADR-23.
  - **Markdown element styling**: rendered elements (headings h1–h6, bold, italic, strikethrough, inline code, blockquotes) must visually match GitHub Dark High Contrast — type scale, font weight, and emphasis conventions, not only colors.

### Spike: does markdown_live_editor work on iOS Safari, and is Web Share reachable at all?

**Branch**: `chore/web-editor-ios-spike`
**Commit type**: `chore:` — a throwaway validation harness, not a shipped user-facing capability. This is explicitly a go/no-go spike (Phase 0 of `notes/dev/web_platform.md`), not the start of the real feature.

**Context**: The project owner wants a web version of QuKi-Notes, specifically scoped as an installable iOS PWA with share-out — a stopgap for deferred native iOS builds, not a general "web app for any browser." Full spec: `notes/dev/web_platform.md` (read it in full before starting — it explains what's in/out of scope and why, including that File System Access API and general desktop-browser support are deliberately *not* goals here).

Before any real implementation work (storage abstraction, the actual transport, PWA packaging) is worth starting, two unknowns need real answers, because guessing wrong on either invalidates everything built on top:

1. **Does `markdown_live_editor` (`packages/markdown_live_editor/`) actually work in a browser at all**, specifically **real iOS Safari** — not desktop Chrome, not "a browser" generically. It's a from-scratch `RenderObject` + `TextInputClient` (ADR-31), not a stock `TextField`, and this project has an extensive, documented history of real pain getting text input/focus/keyboard behavior right on just Android and Windows (`notes/dev/keyboard_focus_state.md`, the ADR-36 selection effort, root `CLAUDE.md`'s Known Bugs). WebKit/Safari is the most divergent browser engine for exactly this category of bug (IME composition, on-screen-keyboard viewport handling, selection/caret quirks), and this project has zero prior experience with it. Desktop Chrome working does not predict iOS Safari working.
2. **Is `navigator.share()` (Web Share API) actually reachable from iOS Safari / an installed PWA at all** — the mechanism the whole "share-out" goal depends on.

**What to build**: a minimal, throwaway Flutter Web harness — deliberately *not* the full QuKi-Notes app. Import `markdown_live_editor` directly as a package dependency into a bare-bones Flutter Web project/entry point (a new small scaffold is fine; this does not need to reuse `lib/main.dart` or anything in `lib/core/`). Reasoning for keeping it separate from the main app: the main app's storage layer (`lib/core/storage/`) uses `dart:io` directly, which won't even compile for web — that's a real, already-known, separate problem for a later phase (see `web_platform.md` §4), not something this spike needs to solve or work around. Scoping the harness to just the editor package sidesteps that entirely and keeps this spike focused on the two actual unknowns above.

The harness needs:
- The editor rendering and accepting real keyboard/touch input (enough surface to test typing, IME composition — try a non-Latin input method if you have one available, or at minimum confirm composition-in-progress text behaves sanely — selection via tap/drag, and confirm the custom paint path (checkboxes, list markers, etc.) actually renders instead of erroring or blanking).
- A single, isolated button/action that calls `navigator.share()` (via `package:web` or `dart:js_interop` — whichever is the current non-deprecated approach; do not use `dart:html`, which is being phased out) with some placeholder text, gated by `navigator.canShare()` first per `web_platform.md` §5's guidance about not assuming it works. Keep the tap-to-call chain short and direct, not routed through unrelated async work first — §5 explains why (this project's own recent, hard-lesson from the Android share bug about async gaps before a native share call).

**You cannot fully verify this yourself** — there's no real iOS device or Simulator in this environment. What you *can* and must do:
- Get the harness actually building and running for web (`flutter build web` or `flutter run -d chrome` from wherever it lives) and confirm it works in a desktop browser as a baseline sanity check — this tells you the harness itself isn't broken, not that iOS Safari will behave the same.
- Set it up so the project owner can open it on a real iPhone with minimal friction — e.g. `flutter run -d web-server --web-hostname=0.0.0.0 --web-port=<port>` and clear instructions for reaching it from a phone on the same network, or however you judge is simplest. State exactly what you did and what URL/steps the project owner needs.
- Write up, in your report, precisely what still needs real iOS Safari confirmation and what (if anything) already looks broken or promising from the desktop-browser sanity check — don't blur "I got it running in Chrome" into "this works."

**Explicitly out of scope**: the actual storage abstraction, the real `WebShareTransport` transport-plugin implementation, PWA manifest/installability packaging, and touching the main QuKi-Notes app (`lib/`) at all. This spike's only job is answering the two questions above as concretely as possible before any of that is worth starting.

**Checklist**: `dart format`, `flutter analyze` on whatever you create. No `flutter test` requirement in the usual sense — this is a throwaway spike, not shipped code; use your judgment on whether any assertion-based test is actually useful here versus manual verification being the only meaningful signal. Report back: exact steps for the project owner to open this on their iPhone, what you verified yourself (desktop browser only) versus what's still unconfirmed, and anything you noticed that already looks like a red flag (even from desktop testing) worth flagging before further investment.

**Explicitly out of scope**: #338/#339 — unrelated, already investigated separately. The diagnostic instrumentation from PR #403 — this branch is off `main` and does not include it; if this fix doesn't fully resolve the repro, that instrumentation is still available separately to merge in later for further investigation.

**On test coverage and claiming this fixed**: same discipline as every task in this slot — this is a real device-timing/OS-mechanism bug. Do not describe this as fixed, resolved, or complete in your report, PR title, or any doc update, even if it looks correct and passes everything you can run locally. The project owner needs to run the specific repro chain above (target closed / target already open / repeat share after another app's share) enough times to have real confidence, not just once.

**Checklist**: `dart format`, `flutter analyze`, root tests (`flutter test` from repo root). Report back: what you changed and why, whether you found reason to deviate from the reference-implementation combination above, what you verified automatically, and exactly what's still pending the project owner's on-device pass through the full repro chain.

### DEFERRED — Feature: trash auto-purge — fixed 30-day retention (ADR-38, #368)

**Do not start this without explicit go-ahead from the project owner.** Kept here ready-to-launch, not as an active assignment.

**Branch**: `feat/trash-auto-purge`
**Commit type**: `feat:` — genuinely new capability (reverses the prior "no timer" decision), not closing a gap in previously-declared behavior.

Read `notes/dev/decisions.md` → ADR-38 in full before starting. It is already locked by the project owner — the "what" is not open for renegotiation, only your implementation approach.

**What to build**: items sitting in `.trash/` are automatically, permanently purged 30 days after the date they were moved there. Fixed at exactly 30 days — no settings, no configurability, no UI countdown or expiry display anywhere. The existing Recently Deleted screen's tap-to-restore / swipe-to-hard-delete behavior for anything not yet expired is completely unchanged.

**Correctness invariants** (mechanism is yours to design — not prescribed):

1. **Record deletion time.** `QuKiStorage.softDelete()` (`lib/core/storage/quki_storage.dart`) currently moves `{uuid}.md` + `.meta/{uuid}.json` into `.trash/` unchanged — nothing in the sidecar marks when that move happened. A `deletedAt` timestamp must be recorded at the moment of soft-delete. Where it lives (extend the existing meta sidecar schema, a new field, a new file) is your call.

2. **Grandfather existing trash on first contact.** Any item already sitting in `.trash/` when this ships has no real `deletedAt`. The first time the sweep examines such an item, it must assign it a fresh `deletedAt` (the current time) — not backdate it, not treat it as pre-expired — and that assignment must persist (write it back), so the item isn't re-grandfathered on every subsequent launch. Net invariant: nothing already in trash before this feature ships is ever purged as a side effect of the app updating; it gets a full fresh 30-day window starting from whenever the app first checks it.

3. **Purge reuses the existing hard-delete path.** Sweeping is not a new deletion mechanism — for any trash item whose `deletedAt` is ≥30 days in the past, call the same `hardDelete()` (or equivalent) the Recently Deleted screen's swipe-to-hard-delete gesture already uses.

4. **Runs once per app startup** — a single check at launch, not on every Recently Deleted screen open or `TrashIndex` rebuild.

5. **Must not block or visibly delay cold launch.** This app has a repeated, project-owner-confirmed history of broken cold-launch work (auto-focus shipped as "Complete" three separate times without ever functioning — see root `CLAUDE.md`'s Known bugs and `notes/dev/decisions.md`). The sweep must not become a fourth entry in that pattern: it must run without holding up first-frame render or making the app feel slower to open (fire-and-forget after first frame, a separate isolate, or another approach — you decide). **If you cannot make it fully invisible/non-blocking**, the fallback is an explicit, non-modal, transient loading indicator — e.g. a snackbar reading something like "Cleaning up trash…" — shown only while the sweep is actively running, auto-dismissing when it finishes. Do not silently block startup and hope it isn't noticed; either make it invisible, or tell the user what's happening while it runs. This snackbar (only if actually needed) is the *only* new UI this feature is allowed to add.

6. **No settings, no per-item countdown/expiry UI anywhere** — this is a silent background rule, not a feature to expose to the user.

**Explicitly out of scope**: any UI for viewing/adjusting the retention period; any per-item "expires in N days" display on the Recently Deleted list; any change to the existing tap-to-restore / swipe-to-hard-delete flow for unexpired items; any change to soft-delete's behavior beyond adding `deletedAt`.

**Required test coverage**:
- An item past the 30-day mark gets hard-deleted by the sweep; an item not yet past does not.
- Boundary case: exactly at 30 days — decide and test which side of the boundary is authoritative, and document your choice in your report.
- Grandfathering: an item with no `deletedAt` (simulating pre-existing trash) is NOT purged on the sweep that first encounters it, gets a `deletedAt` assigned, and that assignment persists (a second sweep shortly after neither re-grandfathers nor purges it early).
- The sweep never touches active (non-trashed) QuKis.
- The sweep runs once at startup, not repeatedly on every trash-related screen visit.
- If you implement the fallback snackbar: cover that it only appears while the sweep is actually running, and does not appear when the sweep is fast/invisible. If this specific behavior isn't practically testable, explain why in your report and how you verified it manually instead.

**Checklist**: `dart format`, `flutter analyze`, root tests (`flutter test` from repo root). This touches `lib/core/storage/` and app bootstrap, not the `markdown_live_editor` package — skip package tests unless you end up touching that package, in which case run those too. Report back: where you stored `deletedAt`, how the startup sweep is triggered/scheduled, whether you achieved a fully invisible sweep or needed the fallback snackbar (and how you verified startup isn't perceptibly slower either way), and test evidence for every invariant above.
