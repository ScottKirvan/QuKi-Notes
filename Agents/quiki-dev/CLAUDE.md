### Nested list indentation — ADR-34 Stages 2+3 combined (#241)

**Branch**: `feat/block-indentation-stage2`
**Commit type**: `feat:` — genuinely new capability (nested lists don't render at all today; indented lines currently fall through to plain-paragraph text).
**Suggested PR title** (Spec opens the PR, not you): `feat(editor): nested list indentation (ADR-34 Stages 2+3, #241)`

**Read first, in this order**: `notes/dev/block_indentation.md` (the full spec, including the Stage 2+3 combination reasoning — read all of it) and `notes/dev/decisions.md` → ADR-34. Then read `packages/markdown_live_editor/lib/src/md_parser.dart`'s `MdParser.parse()` in full — specifically the list/checkbox/ol detection steps (all `line.startsWith(...)`, anchored at column 0) and `_blockquoteDepth()` (the nesting-depth pattern ADR-34 Stage 1 already established for blockquotes, which you're mirroring for lists). Then read `RenderModel._computeRuns()` in `render_model.dart` (currently only reads `indentLevel` for `MdElKind.blockquote` — see the `if (block != null && block.kind == MdElKind.blockquote)` check) and `QuikiRenderEditor`'s run-layout mechanism it feeds (`_RunLayout`, `_runForRendered`, `performLayout()`) from Stage 1 — this is the rendering foundation you're wiring into, not rebuilding. Also read `markdown_editor.dart`'s `_onTextChanged`/`_listContinuation`/`_listPrefixLength` (list auto-continue on Enter) — the regexes there (`_taskPrefixRe`, `_unorderedPrefixRe`, `_orderedRe`) are anchored with `^` at the start of the line.

**Why this is one brief, not two stages**: `notes/dev/block_indentation.md`'s original plan split "parser detects list indent" from "wire it into rendering" as separately-shippable stages (the same pattern ADR-33 used). That doesn't work cleanly here: today, an indented list line (`  - sub-item`) falls through to plain-paragraph handling and renders as literal text. If the parser alone were taught to recognize it as a list item, it would immediately start rendering as a bullet/checkbox glyph — but flush at the left margin, indistinguishable from a top-level item, since nothing yet tells the renderer to indent it. That's a regression-shaped intermediate state, not a clean incremental one. Build both together.

**What to build**:

1. **Parser**: `MdParser.parse()`'s list-item detection (`ul`, `ol`, `checkboxUnchecked`, `checkboxChecked`) must recognize indented markers, not just column 0. Detect each line's leading whitespace before the marker and compute an integer nesting depth from it, stored in `MdElement.indentLevel` — the same kind-agnostic field ADR-34 Stage 1 introduced, currently only set for blockquotes. The exact indent-unit-to-depth mapping (spaces per level, tab handling, how irregular/mixed indentation is resolved) is your design choice — CommonMark's real rule is relative to the parent item's content column, which is more machinery than this codebase needs; a simpler fixed-unit heuristic is consistent with the permissive-heuristic pattern already used for `_blockquoteDepth()` and the Stage 3 HTML-line detection (ADR-33). Pick something internally consistent, document your reasoning, and test it.
2. **Ordered-list numbering at depth**: decide what happens when an `ol` block changes nesting depth mid-sequence — e.g. `1. / 1. / 1.` where the second and third lines are indented one level deeper than the first. Each distinct nesting level's consecutive-numbering state (today tracked via `olBlockStart`/`olRunCount`) should behave as its own list, restarting its own sequence, not continuing the parent level's count across a depth change. This is a correctness invariant worth an explicit test with asserted sequence numbers, not just "doesn't crash."
3. **Rendering**: `RenderModel._computeRuns()` currently special-cases `MdElKind.blockquote` to read `indentLevel` into layout runs. Generalize this so list-kind elements (`ul`, `ol`, `checkboxUnchecked`, `checkboxChecked`) contribute their `indentLevel` to run boundaries the same way. `QuikiRenderEditor` already lays out and paints per run (ADR-34 Stage 1) — this stage should not need to touch its public coordinate API at all. If you find yourself needing to change `positionForOffset`, `getOffsetForCaret`, `getPositionForOffset`, `preferredLineHeight`, `textHeight`, `linkUrlForOffset`, or `checkboxSourceOffsetForTap`'s signatures, or `quiki_editor.dart`'s calling code, stop and flag it back to me — that's a signal something about Stage 1's contract didn't generalize the way expected.
4. **List auto-continue preserves indentation**: pressing Enter after an indented list item must continue at the *same* indentation level — insert the next marker with the completed line's own leading whitespace, not reset to column 0. This is about preserving whatever indentation a line already has, not creating new indentation. Explicitly excluded (see below): using Tab/Shift+Tab to create or change an indentation level interactively.

**Explicitly out of scope for this PR — do not implement, and do not decide to defer something else instead without flagging it back to me first**:
- Tab/Shift+Tab interactive indent creation or adjustment (#77) — its own future brief, once this lands.
- Nested blockquote-inside-list or list-inside-blockquote (combining the two block kinds in one nested structure) — each kind's own nesting is in scope; combining kinds is a new, harder question not covered here.
- Pixel-perfect matching of every GFM edge case for mixed ordered/unordered nesting beyond the one required invariant above (independent numbering per nesting level) — structurally reasonable and non-crashing is the bar, not exhaustive CommonMark conformance.
- Inline image parsing — still on hold pending the project owner's own testing; do not touch anything image-related.
- Tables.

**Tests required**:
- Existing top-level (indent-level-0) list/ol/checkbox behavior is byte-identical — every existing test in the package suite must keep passing unmodified. Same emphasis as Stage 1: any regression here is a blocker, not a tradeoff.
- Indented list-item detection: your chosen indent unit, applied to `-`/`*`/`+`, ol digit markers, and checkbox markers, correctly recognized and given the right depth — at least a 2-level-deep case, not just depth 0 vs 1.
- Ordered-list numbering restarts independently at each new nesting level (the invariant from point 2 above) — assert actual sequence numbers.
- A nested list item long enough to word-wrap has every wrapped visual row indented correctly — mirror the wrapped-blockquote-line regression test Stage 1 wrote for this exact class of bug.
- List auto-continue preserves indentation when continuing a nested item via Enter.
- A document mixing a nested list and a nested blockquote doesn't corrupt either's layout runs — both kinds now feed the same `_computeRuns` mechanism.
- Tap-to-source, checkbox tap-to-toggle, and link tap-to-navigate still correct inside a nested list item.
- Anything visual you can't confidently assert without a device should be flagged honestly in your report, not asserted past your real confidence — same standard as Stage 1.
