### Nested inline markdown — Stage 4 addendum round 3 (blockquote indent + stripe alignment)

**This is additional work on the existing `fix/nested-inline-markdown-stage4` branch, not a new branch.** Two earlier rounds already landed on this branch and are done: bare `>` marker recognition, the empty-blockquote stripe off-by-one, and stripe continuity across wrapped/multi-line content are all fixed and confirmed working. Two issues remain, found via direct before/after comparison against real GitHub rendering of the same markdown (screenshots in the conversation this brief was written from — not available to you, but described precisely below).

**Branch**: `fix/nested-inline-markdown-stage4` (checkout the existing branch — do not create a new one, do not rebase/force-push, just add commits on top).
**Commit type**: `fix:`.
**PR**: already open as #283 (Spec updates it, not you) — same "do not open a PR" rule as always applies; push the branch and report back.

**Read first**: `notes/dev/nested_inline_markdown.md` and `notes/dev/decisions.md` → ADR-33. Read the current state of `packages/markdown_live_editor/lib/src/md_parser.dart` (blockquote branch and `MdElement.collapsedMarker`), `render_model.dart` (`BlockquoteSlot`, `groupBlockquoteRuns`), and `quiki_render_editor.dart` (the blockquote stripe paint block) as they exist now on this branch — this round builds on the previous two rounds' work, not from scratch.

**Issue 1 — blockquote content isn't indented relative to plain text.** Confirmed via a widget test rendering both a plain paragraph and a blockquote side by side: their content starts at the exact same horizontal (X) position. Real GitHub/CommonMark blockquotes push the quoted text visibly to the right of normal paragraph text — this isn't just "a small gap next to the stripe," it's genuine indentation of the content itself. Currently blockquote hides its `>`/`> ` marker purely via `isDelimiter` (no substitution), so nothing reserves extra width the way list/checkbox markers do.

Fix direction (not prescribed, but this is the established precedent to follow): checkbox and list markers already solve exactly this kind of "reserve extra rendered width before content" problem via `MdElement.collapsedMarker` — a substitution string of blank characters (or a glyph) that gets emitted in place of the hidden marker, consumed by the existing marker-substitution code path in `RenderModel.build()` (`if (block.collapsedMarker.isNotEmpty && si == block.start) {...}`). Blockquote currently returns `''` from `collapsedMarker` (no substitution at all). Giving blockquote a non-empty `collapsedMarker` (some number of blank characters, reserving real indentation width) would reuse that same already-proven mechanism rather than inventing a new one. Pick a character count that visually matches GitHub's blockquote indent — verify this with the golden-test technique below, it's well suited to checking indentation precisely (box positions are geometrically exact even without real glyph rendering, since a widget test's font fallback renders placeholder boxes rather than real ink — confirmed useful for exactly this kind of check, unlike the vertical-alignment issue below).

**Issue 2 — stripe vertical position is too high relative to the text, by a meaningful amount (rough visual estimate: something like 40-50% of a line-height).** Not a subtle one-pixel-off issue — noticeable enough that the stripe reads as belonging to the *previous* line rather than the blockquote's own content. The current code computes the stripe's top/bottom via `_textPainter.getOffsetForCaret()` at the content's rendered start/end offsets — the same technique already used elsewhere in this codebase to position the actual blinking text cursor (which renders correctly), so the technique isn't inherently wrong, but two rounds of using it for the stripe haven't produced correct alignment. Worth trying a different technique this round: `TextPainter.getBoxesForSelection()` returns actual glyph bounding boxes for a text range, rather than a caret's line-box-relative position — this may align better with where the visible ink actually starts/ends, which is what a border stripe needs to match, as opposed to where a caret (a thin vertical line, less sensitive to line-box-vs-ink-top nuance) needs to sit.

**On verifying these before pushing**: a plain `flutter test` widget test rendering the editor (a `MaterialApp` + `Scaffold` + `MarkdownEditor`, matching the production theme in `lib/app.dart`'s dark `ColorScheme` and `lib/features/editor/editor_screen.dart`'s `MarkdownEditorConfig` — `TextStyle(fontSize: 16, height: 1.4)`, `contentPadding: EdgeInsets.fromLTRB(12, 12, 12, 36)`) plus `matchesGoldenFile(...)` (or `flutter test --update-goldens` to generate one directly) produces a real PNG you can read and visually inspect yourself — no device needed. Important limitation to know before you rely on it: this Flutter test environment renders text as solid placeholder boxes, not real glyphs, so **box positions are geometrically reliable for checking horizontal layout (issue 1) but not for fine-grained vertical text-metrics alignment (issue 2)** — for issue 2, reason carefully about what `getBoxesForSelection` actually returns relative to `textOrigin`, and if you can't reach high confidence the fix is correct, say so explicitly in your report rather than asserting it's fixed. This project's device-test loop is expensive (round-trips through the project owner's phone) — a clearly-flagged "I'm not fully sure, here's why, here's what I'd check next" is much more useful than false confidence.

**While fixing both**: verify — don't just assume — that the stripe color (`#7A828E`) and blockquote text color (`#9EA7B4`) still match the locked Primer Dark High Contrast tokens (root `CLAUDE.md`'s visual design standard); they were already correct before this round, don't regress them.
